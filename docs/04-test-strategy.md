# テスト戦略・テスト結果の記録

> ステータス: ドラフト v0.1（2026-10-14）

## 1. 方針

**「リリース時に壊れていて、修正 PR を何度も出し直す」ことをなくす。**

1. **マージ前（PR）に、リリースと同じ検証をすべて行う。** 実際に配布する vsix をインストールした VS Code で動かすところまで PR の時点で確認する。
2. **main へのマージ後にも全テストを再実行**し、通ったときだけリリースする（マージ後のコードで最終確認）。
3. **結果を必ず残す。** 全テストの結果とスクリーンショットを 1 つのレポート（HTML）にまとめ、PR では Artifacts に、リリースでは Release の添付ファイルとして保存する。
4. **ローカルでも同じテストを 1 コマンドで実行できる**ようにし、PR を出す前に気づけるようにする。

## 2. テストの層

| 層 | 名前 | ツール | 何を確かめるか | 実行タイミング |
|---|---|---|---|---|
| **L1** | ユニットテスト | Vitest | ロジック（検索・ゲームのルール・スコア計算・パズルの可解判定・リンクのインポート/重複判定 等） | ローカル保存時（watch）・PR・リリース |
| **L2** | コンテンツ検証 | Vitest + JSON Schema | `content/` の全ファイルがスキーマに合っているか、ID 重複・リンク切れ形式（http/https 以外）・必須項目漏れがないか | PR・リリース |
| **L2** | コード例の実行 | jshell / Python / Node.js / Ruby | チートシートの全コード例が実際に動くか。エラーメッセージ辞書の例のコードが、期待したエラーメッセージを出すか。コード問題の正解の出力・バグの有無。判定が機能していることを「必ず失敗するコード」「エラーにならないコード」で毎回確認する | PR・リリース |
| **L2** | コンテナの起動 | Docker（`npm run test:container`） | 生成した Dockerfile・compose.yaml で小さなサンプル（`tests/fixtures/container/`: Spring Boot + Maven / Gradle・Node）を実際にビルド・起動し、アプリが DB などに繋がってヘルスチェックが UP になるか | PR・リリース（CI の別ジョブ `container`、Linux のみ） |
| **L3** | Webview 画面テスト | Playwright（Chromium） + 擬似 VS Code API | 各機能の画面が表示され、キーボード操作で一通り動くか。**3 テーマのスクリーンショット**、見た目の差分（ビジュアル回帰）、アクセシビリティ（axe-core） | PR・リリース |
| **L4** | VS Code 統合テスト | `@vscode/test-cli`（Mocha） | 実際の VS Code 上で拡張が起動し、コマンド登録・ツリー表示・全機能のパネルが開くこと・設定・保存・リンクのインポート/エクスポートが動くか | PR・リリース（**VS Code 1.120.0 と最新版**、Linux + Windows） |
| **L5** | パッケージ検証 | `vsce package` + スクリプト | vsix に必要なファイルが入っているか（`dist/`・`media/`・コンテンツ JSON）、不要なファイル（`src/`・テスト・`node_modules`）が入っていないか、サイズ上限 | PR・リリース |
| **L6** | 実機 E2E（スモーク） | Playwright（Electron モード） | **作成した vsix をインストールした素の VS Code 1.120.0** を起動し、アクティビティバーのアイコン → メニュー → 各機能を開く → 主要操作、を画面ごとにスクリーンショット | PR・リリース |
| L7 | 手動確認 | PR テンプレートのチェックリスト | 遊んで面白いか・文言・操作感など自動化できない部分。UI 変更時はスクリーンショットを PR に貼る | PR |

> L5・L6 は「ビルドは通るのに、配布した vsix だとファイルが足りなくて動かない」という**リリース時に起きやすい事故**を防ぐための層。

## 3. 各層の詳細

### L1 ユニットテスト
- 対象: `src/features/*/logic.ts` などの DOM 非依存コード、`src/core/` のうち VS Code API に依存しない部分。
- VS Code API に依存する部分は、インターフェース（例: `Storage`）越しに使い、テストではフェイク実装を渡す。
- 乱数・時刻は引数で注入し、テストでは固定する。
- **カバレッジ基準**（下回ったら CI 失敗）: `src/features/**/logic*.ts` 行 80%、`src/core/**` 行 70%。

### L2 コンテンツ検証
- `content/schemas/*.schema.json` で全ファイルを検証。
- 追加チェック: ID の重複、URL が `https://`（または `http://`）で始まるか、`danger: true` のコマンドに注意文があるか、チートシートが共通の目次構成に沿っているか。
- テスト用の不正データ（`tests/fixtures/content-invalid/`）で「ちゃんと失敗すること」も確認する。

### L2 コード例の実行（`npm run test:snippets`）
- チートシート（言語）の全コード例を実際の処理系（jshell / Python / Node.js / Ruby）で実行し、**エラーにならない**ことを確かめる。判定が機能していることを、言語ごとの「必ず失敗するコード」で毎回確認する。
- エラーメッセージ辞書（`content/errors/`）の例のコードは逆に、次をすべて満たすことを確かめる（`scripts/snippet-checks.ts` の `checkErrorExample`）。
  - **エラーになる**こと（Java は jshell のため、コンパイルエラーは `Error:`、実行時例外は `Exception java.lang.〇〇` の形で出る。英語表示にして判定する）
  - 出力（標準エラーを含む）に `expect` の文字列が含まれること
  - 出力をそのまま貼り付けて検索したとき、同じ言語の中でそのエラーが先頭に来ること（`patterns` が実際のメッセージに含まれ、ほかのエラーより長く一致する）
  - 検査が機能していることを、言語ごとの「エラーにならないコード」が不合格になることで毎回確認する。
- コード問題（quiz-kit。`scripts/quiz-snippets.ts`・`scripts/quiz-checks.ts`）。出力は改行コード・各行の末尾の空白・最後の改行をそろえてから比べる（行頭の空白・途中の空行は比べる。`src/core/codeQuiz.ts` の `normalizeOutput`）。
  - 出力当て（`content/output-quiz/`）: エラーにならず、**標準出力が正解（`answer`）と一致**し、誤答の選択肢がどれも実際の出力と違うこと
  - バグ探し（`content/bug-hunt/`）: **出力が期待する出力（`expected`）と違う**（エラーで止まるのも可）＝本当にバグがあること。さらに検査専用の修正行（`fix`。画面と dist には出さない）を当てると、エラーにならず期待どおりになること
  - 検査が機能していることを、言語ごとに「わざと間違えた正解」「実際の出力と同じ誤答」「バグの無いコード」「修正してもエラーになるコード」が不合格になることで毎回確認する。
- 処理系が無い言語はスキップとして記録する（CI ではスキップがあると失敗）。

### L3 Webview 画面テスト
- 仕組み: テスト用の HTML ページ（`tests/webview/harness/`）でビルド済みの `dist/webview/<id>.js` を読み込み、`acquireVsCodeApi()` を**擬似実装**に差し替える。擬似実装はやり取りしたメッセージを記録し、テスト用データを返す。
  - VS Code の Webview は Chromium なので、Playwright の Chromium で見た目・動作の再現性が高い。
- テーマ: VS Code の Light Modern / Dark Modern / Dark High Contrast の CSS 変数セット（`tests/webview/themes/*.css`）を切り替えて実行。
  - Webview の CSS で使った `--vscode-*` 変数がテーマファイルに全て定義されているかを L1 で検査している（`scripts/theme-vars.test.ts`）。定義漏れがあるとスクリーンショットが実際の見た目と違ってしまうため。新しい変数を使ったら 3 テーマすべてに値を追加する。
- 機能ごとに最低限書くテスト:
  | 種類 | 内容 |
  |---|---|
  | 表示 | 初期表示でエラーが出ない（コンソールエラー 0 件）、主要要素がある |
  | 操作 | キーボードだけで主要操作が完了する（ゲームなら 開始 → 一時停止（Esc）→ 再開 → 結果） |
  | 通信 | 期待したメッセージ（`score/submit`・`link/open` 等）が送られる |
  | スクリーンショット | 主要な状態 × 3 テーマ を保存し、前回との見た目の差分を比較 |
  | アクセシビリティ | axe-core で重大な違反（critical / serious）が 0 件 |
- **ビジュアル回帰の基準画像**は `tests/webview/__screenshots__/` にコミットする。フォント差を避けるため、基準画像の更新は CI（Linux）上で行う（手順は 7 章）。

### L4 VS Code 統合テスト
- 実際の VS Code をダウンロードして拡張機能開発モードで起動し、その中でテストを実行する。
- マトリクス:
  | OS | VS Code |
  |---|---|
  | ubuntu-latest | 1.120.0（最低対応バージョン） |
  | ubuntu-latest | stable（最新版） |
  | windows-latest | stable（社内の利用環境） |
- 主なテスト:
  - 拡張が有効化され、全コマンドが登録されている
  - ツリーにすべての機能が表示される（`features/index.ts` の登録数と一致）
  - **全機能のパネルを順に開いて閉じ、エラーが出ない**
  - 設定変更（`games.enabled = false` でゲームが消える 等）が反映される
  - スコア・個人リンクが保存され、拡張の再読み込み後も残る
  - リンクのインポート（正常 / 重複 / 不正行を含むファイル）・エクスポート（JSON / YAML）・共有ファイルの変更検知・信頼されていないワークスペースではワークスペースリンクを読まない
- テストしやすさのための設計ルール: **ファイル選択ダイアログを出すコマンドは、引数で URI を受け取れるようにする**（テストではダイアログを経由せずに実行する）。

### L5 パッケージ検証
- `vsce ls` の結果を検査し、必須ファイルの有無・禁止ファイルの混入をチェック。
- vsix のサイズが上限（初期値 5 MB）を超えたら失敗。
- `package.json` の `engines.vscode` と `@types/vscode` のバージョンが一致しているか確認。

### L6 実機 E2E（スモーク）
- L5 で作った **vsix を、まっさらな VS Code 1.120.0 にインストール**（`--extensions-dir` / `--user-data-dir` を一時フォルダに指定）し、Playwright の Electron モードで起動・操作する（VS Code 本体のスモークテストと同じ方式）。
- シナリオ（全画面のスクリーンショットを各ステップで保存）:
  1. 起動 → アクティビティバーの専用アイコンをクリック → メニューが表示される
  2. ホーム → Linux コマンド辞書で検索 → チートシートで言語切替 → リンク集
  3. 各ゲームを開き、開始 → Esc で一時停止 → 閉じる
  4. コマンドパレットから機能検索で開く
- 失敗時は動画とトレース（操作の記録）も保存する。
- 範囲は「主要な流れが通るか」に絞る（細かい確認は L3・L4 で行う）。VS Code の画面構造の変更で壊れやすいため、セレクタは `tests/e2e/selectors.ts` に集約する。
- 方式は動作確認済み（Windows / VS Code 1.120.0）。将来 VS Code の変更で使えなくなった場合の代替は vscode-extension-tester（Red Hat 製）。
- 注意: VS Code のショートカットはそのまま効く（例: `Ctrl+Shift+W` はウィンドウを閉じる）。タブを閉じる等はボタン操作で行う。

## 4. テスト結果の記録

### 4.1 出力されるもの

```
test-results/
├─ index.html              # ★まとめレポート（これを開けば全部見られる）
│                           #   ・層ごとの成功/失敗件数
│                           #   ・スクリーンショットのギャラリー（機能 × テーマ、E2E の各ステップ）
│                           #   ・各詳細レポートへのリンク
├─ summary.md              # 要約（PR コメント・Job Summary・リリースノートに使用）
├─ unit/                   # JUnit XML、カバレッジ HTML
├─ webview/                # Playwright HTML レポート、スクリーンショット、差分画像
├─ integration/<os>-<ver>/ # JUnit XML、VS Code のログ
├─ package/                # vsix の中身一覧・サイズ
└─ e2e/                    # Playwright HTML レポート、各ステップのスクリーンショット、失敗時の動画・トレース
```

まとめレポートは `scripts/test-report.ts`（`npm run test:report`）で各層の結果から生成する。

### 4.2 保存先

| タイミング | 保存先 | 保存期間 | 見方 |
|---|---|---|---|
| PR | Actions の Artifacts `test-report`（+ `vsix`） | 90 日 | PR の Checks → 該当の実行 → Artifacts からダウンロードして `index.html` を開く |
| PR | PR コメント（自動投稿・更新） | PR が残る限り | 層ごとの件数、失敗したテスト名、Artifacts へのリンク |
| PR / main | Actions の Job Summary | 実行ログが残る限り | 実行結果ページに要約表を表示 |
| リリース | **GitHub Release の添付ファイル** `test-report-v<version>.zip` | 無期限 | Release ページからダウンロード。**どのバージョンがどのテストを通って出たか**の証跡 |
| リリース | リリースノート本文 | 無期限 | テスト結果の要約表 + 自動生成の変更履歴 |

> 拡張案（P2）: スクリーンショットを PR コメントに直接画像で表示する（専用ブランチや GitHub Pages に画像を置いて埋め込む）。

## 5. ローカルでの実行

```bash
npm run verify          # L1〜L3 + L5（数分）。PR を出す前に必ず実行
npm run verify:full     # L1〜L6 すべて（初回は VS Code のダウンロードあり）
npm run test:report     # test-results/index.html を生成
```

| スクリプト | 内容 |
|---|---|
| `test` | L1 + L2（Vitest、カバレッジ付き） |
| `test:webview` | L3（Playwright） |
| `test:webview:update` | L3 の基準画像を更新（原則 CI で実行。7 章） |
| `test:integration` | L4（`@vscode/test-cli`） |
| `test:package` | L5 |
| `test:e2e` | L6 |

- Windows でも実行できること（パス区切り・改行コードに注意。スクリプトは Node で書き、シェル依存のコマンドを使わない）。
- L3 のビジュアル比較は OS によってフォント描画が異なるため、ローカル（Windows）では差分比較をスキップし、スクリーンショットの保存のみ行う（CI の Linux で比較する）。

## 6. CI での流れ（`.github/workflows/ci.yml`）

```
            ┌─▶ webview（L3） ─────────────┐
 build ─────┼─▶ integration（L4 × 3 環境）─┼─▶ report（まとめレポート生成・保存・PR コメント）
 (L1,L2,L5) └─▶ e2e（L6：vsix を使用）─────┘
```

- `build` ジョブで作った vsix を後続のジョブで共有し、**テストした vsix とリリースする vsix を同じものにする**。
- `report` ジョブは、どこかのテストが失敗しても必ず実行し（`if: always()`）、失敗時の記録も残す。
- `release.yml` は `ci.yml` をそのまま呼び出す（再利用ワークフロー）ため、PR とリリースの検証内容は常に同じ。リリースのジョブは main のときだけ動き、`SHA256SUMS` に署名した `SHA256SUMS.sig` も添付する（[開発ルール 5.3](03-development-rules.md#53-リリース)）。
- 権限はジョブごとに最小（既定は読み取りだけ。PR へのコメントが要る report ジョブだけ `pull-requests: write`）。外部の action は SHA で固定し、build ジョブで `npm audit signatures` を確かめる（[開発ルール 4.1](03-development-rules.md#41-依存パッケージci-の安全のための決まり)）。
- `npm ci` の後に `npm run setup` を実行する（`.npmrc` で install スクリプトを止めているため、esbuild だけを動かす）。
- E2E のみ、不安定な失敗に備えて 1 回だけ自動リトライする。リトライで通ったテストはレポートに「不安定」と表示し、Issue 化して直す。

## 7. 運用ルール

- **新機能は L1・L3・L4 のテストをセットで追加する**（`/add-feature` スキルの手順に含まれる）。L6 のシナリオに追加するかはレビューで判断。
- テストのスキップ（`skip` / `only`）はコミットしない。やむを得ずスキップする場合は理由と Issue 番号をコメントに書く。
- 見た目を意図的に変えた場合・新しい画面を追加した場合のビジュアル基準画像の更新:
  1. PR の CI で差分（または「基準画像がありません」）で失敗する → レポートの差分画像で意図どおりか確認
  2. Actions の「Update visual snapshots」ワークフローを手動実行し、入力に PR のブランチ名を入れる（Linux で基準画像を再生成してコミット）
     - 入力できるのは同じリポジトリの作業ブランチ名だけ（`feature/`・`fix/`・`content/`・`refactor/`・`test/`・`docs/`・`chore/`・`security/` で始まる名前）。`main`・`ver*`・`refs/…`・fork の PR は拒否する
     - 画像を作るジョブ（`npm ci`・ビルド・Playwright）は読み取り権限だけで動き、画像を artifact で渡す。push するジョブは npm を動かさずにチェックアウトし直し、画像だけをコミットして入力と同じブランチへ push する
     - 画像を作っている間にそのブランチへ push すると失敗する（もう一度実行する）
  3. **bot のコミットでは CI が再実行されない**（GitHub の仕様）ため、手元で `git pull` してから次のコミットを push する（変更が無ければ `git commit --allow-empty -m "ci: 基準画像の更新後に再実行"`）
  4. レビューで差分画像を確認してもらう
- バグを直したら、そのバグを再現するテストを先に追加する。
- CI の Ubuntu は `ubuntu-24.04` に固定している（`ubuntu-latest` の切り替えでフォント描画が変わると、ビジュアル基準画像が一斉にずれるため）。上げるときは同じ PR で基準画像も更新する。

## 8. リリース前チェック（自動 + 確認）

- [ ] PR の CI がすべて成功（L1〜L6）
- [ ] まとめレポートでスクリーンショットを目視確認（崩れ・文字切れ・テーマ）
- [ ] PR の vsix を自分の VS Code にインストールして触った
- [ ] `package.json` の `version` と `CHANGELOG.md` を更新した
- [ ] マージ後、Release に vsix とテストレポートが添付されたことを確認
